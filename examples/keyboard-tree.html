业务架构图取树接口

给业务架构图的每个节点补一个「有没有关联制度」的标记。路径、入参、其余字段与 平台原接口保持一致，只多返回一个 hasSystemDoc。

成稿 2026-09-04 示例取自 本地实跑 的真实请求响应（作为公开样例，路径与节点名已脱敏）；另有 1 项分支行为待补验证，见 §2

#接口用途

需求「流程资产业务架构图增加显示关联制度图标」要求业务架构图的每个节点知道有没有关联制度，而原来的 平台取树接口 /platform/arch/organization-link*/tree 不返回这个信息。

项目侧新增两个替代接口，内部调用平台的同一套查询，补上 hasSystemDoc 后整树返回。除多这一个字段外，与原接口逐字段完全一致，已实跑对拍。平台原接口保持不动、不下线。

请求参数（query string）

字段类型必填业务含义示例值
idString是业务架构图根节点 id（架构 archId 或流程 wfId）。传不存在的 id 不报错，返回空数组1981332410449883136
subLevelint是向下展开的层数，对应界面上「显示 N 层」。漏传会 400，不是按默认值处理5

入参与 平台原接口逐字保持一致，原来怎么调现在就怎么调，只换 URL。

权限

门户端非管理员按当前用户的权限表达式过滤可见节点，实现与 平台原接口一致。
工作台端平台原接口此处不做权限过滤，本接口保持一致。

非管理员分支尚未实跑 待补验证

截至成稿只用管理员账号做过对拍，而管理员走的是「跳过权限表达式计算」那条分支 —— 非管理员分支还没被真实执行过。拿到普通用户测试账号后需补测：同一账号下，本接口与 平台原接口返回的可见节点集合应完全一致。

返回扁平节点数组，不是嵌套树，层级关系由 parentId 表达 —— 与原接口一致。

hasSystemDoc 的判定口径

两端看的是不同版本的数据，这是业务定的：门户的按门户数据判断，工作台的按工作台数据判断。

门户端看该节点已发布版本的「流程制度」页签有没有记录。
工作台端看该节点最新草稿版本的「流程制度」页签有没有记录。

所以同一个节点在两端可能一真一假。草稿里挂了制度但还没发布时，工作台显示图标、门户不显示 —— 这是预期行为，不是 bug，不要当成数据不一致来排查。下一节用同一个节点的两份真实响应把这件事摊开。

引用节点（reference=true）按被引用的原节点 referencedId 判断，不看自己。

#边界与约束

  • subLevel 不影响 hasSystemDoc 的正确性。它只裁剪返回的节点范围；标记的取数覆盖整棵子树，被裁掉的节点根本不会出现在响应里，不存在「层数调小了标记就变了」的情况。
  • 引用节点指向本子树之外时，标记退化为 false。标记按 referencedId 查，而查询范围限定在本次请求的子树内；被引用的原节点若在别的架构下，查不到就当没有。真要覆盖这种情况需要改成按 id 集合查，届时反馈。
  • 没有分页，一次给完。响应是扁平数组，节点数随架构规模增长，实测门户端 74 条、工作台端 763 条。前端沿用原接口的拼树逻辑即可。
  • 两个「流程制度」页签的配置 id 是客户配置数据，不是常量。服务端通过 app.keyboard-map.system-doc.arch-tab-id 和 .flow-tab-id 配置，默认 archSystemDoc 与 flowSystemDoc。客户若在「要素页签配置」里把页签删了重建，id 会变、标记会集体变 false —— 出现这种情况找后端改配置，不是前端问题。
