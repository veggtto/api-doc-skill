#回调总览

之前你们要拿到工单变化只能轮询 GET /api/tickets/{id}，既有延迟又打不到「标签被删了」这类瞬时动作。事件回调把这件事反过来：你们提供一个 HTTP 地址，我们在事件发生时主动推过去。

整套东西分两半，请分开看：一半是管理接口（你们调我们，用 X-Token 鉴权，就是下面 §2–§5 四个端点）；另一半是回调投递（我们调你们，用 X-Signature 验身，见 §6–§8）。

四个管理端点

使用场景方法与端点鉴权备注
登记一个接收地址 POST/api/webhooks/subscriptions X-Token 响应里带 secret，仅此一次
查看已登记的订阅 GET/api/webhooks/subscriptions X-Token 不返回 secret
取消一个订阅 DELETE/api/webhooks/subscriptions/{id} X-Token 成功 204，无响应体
手动触发一次投递（调试） POST/api/webhooks/test X-Token 发的是固定样例数据，非真实业务数据

鉴权：四个端点都要带请求头 X-Token: demo-token。缺失或值不对一律 401，见失败行为。注意这个令牌只用于管理接口；我们推给你们的回调请求里不带 X-Token，回调的身份验证走签名。

两个事件

目前只有两个事件，events 字段也只接受这两个值，全文一律 ticket.created 在前、label.deleted 在后。

ticket.created工单创建成功后触发。data 就是 POST /api/tickets 那份 201 响应体，字段完全一致
label.deleted标签删除成功后触发。data 是删除瞬间的快照，删完就查不到了，这份快照是你们唯一的信息来源

工单的更新/关闭、标签的创建/修改都不发事件，别按「全量变更流」来设计接收端。

#订阅回调

POST/api/webhooks/subscriptions

请求体

JSON 对象，Content-Type: application/json。

字段类型必填业务含义示例值
urlstring是 接收回调的地址，必须以 http:// 或 https:// 开头。服务端只查前缀，不校验这个地址是否真的通——填错了照样订阅成功，只是事件全部投递失败且没人告诉你 "http://127.0.0.1:9099/hook"
eventsstring[]是 要订阅哪些事件，非空数组，元素只能是 ticket.created / label.deleted。数组里只要有一个不认识的事件名，整个请求 400，不会「忽略掉继续订剩下的」 ["ticket.created","label.deleted"] 
{"url":"http://127.0.0.1:9099/hook","events":["ticket.created","label.deleted"]}

响应字段

成功返回 201，一个对象。

字段类型业务含义示例值
idnumber订阅 id，取消订阅时要用7
urlstring原样回显"http://127.0.0.1:9099/hook"
eventsstring[]原样回显，顺序与请求一致["ticket.created","label.deleted"]
secretstring验签密钥，固定 whsec_ 前缀 + 8 位十六进制。只在这一个响应里出现，列表接口不返回，也没有查看或重置的端点"whsec_a6d91800"

完整请求响应

示例地址 127.0.0.1:8765 是本地验证环境，联调时换成我们给的域名。

POST http://127.0.0.1:8765/api/webhooks/subscriptions
X-Token: demo-token
Content-Type: application/json

{"url":"http://127.0.0.1:9099/hook","events":["ticket.created","label.deleted"]}
201 Created

{"id": 7, "url": "http://127.0.0.1:9099/hook", "events": ["ticket.created", "label.deleted"], "secret": "whsec_a6d91800"}

secret 拿到手就存起来

实跑确认：GET /api/webhooks/subscriptions 的返回里没有 secret 字段，服务端也没有提供任何找回或重置的方式。密钥丢了只能删掉订阅重新订一次，重订会拿到新的 id 和新的 secret，期间产生的事件不会补发。

#回调请求

下面是我们发给你们的请求。方法固定 POST，Content-Type: application/json，请求体 UTF-8 编码。

请求头

头类型业务含义示例值
X-Eventstring事件名，与请求体里的 event 一致。接收端按它分支即可，不必先解 JSONticket.created
X-Delivery-Idstring本次投递的 uuid4。重试会复用同一个值，是去重的依据，注意范围见 §87eb3cf3b-c0ea-4394-b8ef-c6f0b7801e2b
X-Signaturestringsha256= + 64 位十六进制，验签见 §7sha256=b790d2c1…53fc73e1

没有 X-Token，也没有任何标识订阅 id 的头。前者意味着回调请求不携带我们的管理令牌，你们要靠 X-Signature 判断真伪；后者是个已知缺口，一个地址订多次时会出问题，见 §9。

请求体外层

字段类型业务含义示例值
eventstring事件名，与 X-Event 相同"ticket.created"
deliveryIdstring与 X-Delivery-Id 相同"7eb3cf3b-c0ea-4394-b8ef-c6f0b7801e2b"
occurredAtstring事件发生时间，UTC，格式固定 YYYY-MM-DDTHH:MM:SSZ。只精确到秒，没有毫秒，同一秒内的多个事件靠它排不出先后"2026-09-05T04:11:38Z"
dataobject事件数据，结构随 event 完全不同，见下面两张表见下两表

ticket.created 的 data

与 POST /api/tickets 的 201 响应体逐字段一致，没有增删。

接收端该怎么应答

  • 返回 2xx 表示已接收，任何非 2xx 都会触发重试。4xx 也照样重试——实跑用固定返回 403 的接收端验过，服务端不区分「你明确拒绝」和「你挂了」，一律重试满 3 次。所以接收端别用 4xx 表达「这条我不要」，那只会让同一条事件再来两次；不想要的事件请直接返回 2xx 丢弃，或者干脆不订阅它。
  • 响应体内容我们不读也不解析，返回空体也可以，状态码是唯一信号。
  • 必须在 3 秒内应答，这是硬超时，见 §8。

#签名校验

回调请求不带管理令牌，X-Signature 是你们判断「这条请求确实来自我们」的唯一依据。

X-Signature = "sha256=" + HMAC_SHA256(key = 订阅的 secret, message = HTTP 请求体的原始字节).hex()
  • key 是 secret 的完整字符串，包含 whsec_ 前缀，按 UTF-8 取字节，不做任何解码。
  • message 必须是原始请求体字节，不能是「解析后再序列化」的结果。我们发的 JSON 里非 ASCII 字符是原样 UTF-8，没有转成 \u 转义；多数语言的 JSON 库默认会转义，一旦你先 parse 再 stringify，字节就变了，验签必然失败。请在框架读取 body 的最早阶段留一份 raw bytes。
  • 十六进制小写，比较时用常量时间比较，别用普通字符串相等。
  • 签名只覆盖请求体，不覆盖请求头，也不含时间戳——协议本身没有防重放能力，请依赖 deliveryId 去重（§8）。
回归证据：验签是怎么验的，怎么排除的循环验证

基准不是服务端那段代码，而是一个独立进程：另起一个独立的 Python 接收端，把落到线上的请求头和 body 原样存盘，再用标准库 hmac 按上面的公式独立算一遍，跟服务端下发的 X-Signature 比。两边只共享 secret 这一个输入，不共享任何代码路径。

#重试与丢弃

最多投 3 次，间隔 1 秒、3 秒，之后放弃。即首次失败后约 1 秒重试第二次，再约 3 秒重试第三次，全程约 4 秒结束。

接收端表现是否算失败实测尝试次数
返回 2xx否，立即结束1
返回 500是3（间隔实测 1s / 3s）
返回 403（明确拒绝）是，与 5xx 同等对待3（间隔实测 1s / 3s，deliveryId 三次相同）
端口无人监听（连接被拒）是3（第 3 次时把接收端起起来，投递成功落地）
响应慢于 3 秒（硬超时）是3

慢接收端会把同一个事件处理 3 遍

实跑验证：接收端 sleep 5 秒后返回 200，服务端在 3 秒时已经判超时，接收端明明每次都成功返回，仍然收到并执行了 3 次同一事件。请先返回 2xx，再把业务处理丢到异步队列，不要在回调请求里做耗时操作。

去重：deliveryId 管得着什么、管不着什么

  • 管得着重试：同一次投递的 3 次尝试，X-Delivery-Id 是同一个值。按它做幂等，能挡掉重试造成的重复。
  • 管不着扇出：同一个业务变更投给两条订阅时，是两个不同的 deliveryId。如果你们不小心把同一个地址订了两次，按 deliveryId 去重挡不住这种重复。
  • 要按业务去重，请用 event + data.id 组合。
回归证据：重试次数与间隔怎么测的

基准是接收端自己记的时间戳，不是服务端日志——服务端日志和投递逻辑同源，拿它验投递等于自证。接收端把每次收到的请求按 X-Delivery-Id 分组计数并记下到达时刻：

触发时刻 12:09:01
/hook 2d3138e1-8793-494a-9e26-e9348f92f0dd attempts=1 ['12:09:01']
/fail 06b7d612-a8a7-4c2e-a033-66ef17d55f19 attempts=3 ['12:09:01', '12:09:02', '12:09:05']

/fail 固定返回 500，三次尝试的到达时刻间隔正好是 1 秒和 3 秒，且三次的 X-Delivery-Id 完全相同。/hook 返回 200，只来一次。

「连接被拒也重试」的验法：先触发事件，此时目标端口无人监听（第 1、2 次尝试必然失败），2 秒后才把接收端启动起来；如果不重试，这条事件应该永远收不到。实测在触发后约 4 秒（即第 3 次尝试的时刻）收到了它：

12:10:40 /dead 032ebfe0-2cb5-4a84-8b4b-7d6b4d18a51d

#边界与约束

  • 同一个 url 可以重复订阅，服务端不做去重。实跑中把同一地址订了两次，一次建单就收到 2 条投递。麻烦在于：两条投递的 deliveryId 不同，签名分别用各自订阅的 secret，而投递请求里没有任何标识订阅 id 的头——接收端拿到一条请求，没法知道该用哪把密钥。实测一条投递只能被它自己那把 secret 验过，另一把必然失败。所以：同一个地址只订一次。确实需要多订的，只能对该地址持有的所有 secret 逐个尝试，直到有一个验过。
  • 投递是异步的，不会阻塞我们的业务接口。挂着一个 5 秒才响应的订阅时，POST /api/webhooks/test 仍在 0.03 秒返回。好处是我们这边不会被你们拖慢；代价是接口返回成功不代表事件已经投出去，两件事完全解耦。
  • 没有投递顺序保证。每条投递各起一个线程，先发生的事件不一定先到，重试还会进一步打乱。接收端不要依赖到达顺序，要排序请用 data.id（自增）而不是 occurredAt（只到秒，同秒事件分不出先后）。
  • 没有补投、没有历史查询、没有投递状态接口。3 次尝试都失败，这条事件就彻底没了，服务端只在自己的标准输出打一行日志，你们和我们都无法事后查到丢了哪些。这也是为什么接收端要尽快返回 2xx。当前实现是 demo 级的，不能丢事件的场景要不要补一张投递记录表，属于待决策事项——找服务端负责人确认，本文档不代表任何排期承诺。
  • 订阅是全局的，没有租户或来源隔离。订阅之后，这台服务上所有调用方产生的事件都会推给你们，不只是你们自己触发的。验证期间实测到了：接收端收到了十几条由其他调用方在同一台服务上创建工单产生的事件。接收端不要假设收到的事件都是自己触发的，也不要用它来做「我的请求成功了没」的回执。
  • 只有两个事件，且都是「已完成」时态。没有 ticket.updated / ticket.closed / label.created / label.updated。标签删除是软删除，重复删除同一个标签第二次返回 404 且不再发事件，所以不会因为重复调用产生重复事件。
  • url 需要从我们服务所在的机器能访问到。示例里的 127.0.0.1:9099 之所以能通，是因为接收端和服务跑在同一台机器上。联调时请给一个我们这边网络可达的地址，内网地址请先确认连通性——填了不通的地址订阅一样返回 201，不会有任何报错提示。
  • 没有分页、没有条数上限的说明。GET /api/webhooks/subscriptions 一次返全量，订阅总数目前没有限制，也没有配额校验。

两项环境相关行为待补验证 待补验证

  • 服务重启后订阅是否还在：项目 README 写的是数据只放内存、重启即清空，按此推断订阅也会丢、需要重新登记。但这是共享的开发环境，当时有其他调用方在用，没有重启服务去实测。补测方法：找一个没人用的时段，登记一条订阅 → 重启 server.py → GET /api/webhooks/subscriptions 看是否为空。在验证之前，请按「重启后需要重新订阅」来设计你们的接入流程。
  • https 接收地址与 TLS 校验：实跑用的全部是 http://127.0.0.1 本地地址。https:// 前缀能通过参数校验（这一点验过了），但服务端能否成功投递到一个真实的 https 端点、对自签名证书是什么行为，都没有实测。补测方法：等你们的测试环境地址就绪后，先用 POST /api/webhooks/test 打一发，确认接收端收到再接真实事件。

失败行为 均已实跑

下面每一行的状态码和响应体都是实跑抄回来的原文。管理接口的错误响应一律是 JSON 对象，参数类错误带 field 指出是哪个字段。

场景状态码响应体
缺 X-Token 头，或令牌值不对401{"code": "UNAUTHORIZED", "message": "invalid token"}
url 缺失，或不以 http:// / https:// 开头400{"code": "INVALID_PARAM", "field": "url", "message": "url is required and must start with http:// or https://"}
events 缺失、不是数组、或是空数组400{"code": "INVALID_PARAM", "field": "events", "message": "events is required and must be a non-empty array"}
events 里含未知事件名400{"code": "INVALID_PARAM", "field": "events", "message": "events may only contain ticket.created or label.deleted"}
请求体为空、不是合法 JSON、或不是对象（如传数组）400{"code": "BAD_JSON"}
/webhooks/test 的 event 缺失或不认识400{"code": "INVALID_PARAM", "field": "event", "message": "event must be one of ticket.created, label.deleted"}
取消一个不存在（或已取消）的订阅404{"code": "NOT_FOUND"}
端点存在但方法不支持，如 PUT /subscriptions、GET /subscriptions/{id}405{"code": "METHOD_NOT_ALLOWED"}

没有独立的业务错误码体系，code 就是上面这几个字符串。空结果算正常：没有任何订阅时 GET 返回 200 加 []，没有匹配订阅时 /webhooks/test 返回 200 加 {"dispatched": 0}，都不是错误。

投递方向没有错误码——我们不会因为你们返回 4xx 就取消订阅，只是重试 3 次后放弃这一条事件，订阅本身始终保留。
