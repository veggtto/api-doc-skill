# 接口文档生成

产出一份自包含 HTML，调用方双击就能看、能直接转发。样式和交互由 `assets/template.html` 提供，本文件规定**什么时候写、写什么、什么不能写**。

## 触发时机

- 接口实跑通之后的收尾步骤（首选，素材现成）
- 改动新增/变更了对外 Web 接口，需要交付给调用方
- 用户要"把接口文档发给前端/对接方"

**不要在接口还没实跑通之前写。** 没有真实请求响应就没有素材，写出来的是猜测。

## 落盘位置

默认 `<项目根>/doc/api/<feature>.html`；项目已有约定就跟项目的。

同名文件已存在 → **追加"改动历史"行，不覆盖既有内容**。

## 硬规则

1. **素材必须来自实跑**。请求示例、响应示例、边界行为、返回条数，全部抄真实跑通的那一份，不要根据代码意图凭空写。
2. **没验到的必须如实标注**，用 `.warn` 块 + `.tag.todo` 徽标写清楚"为什么没验到、怎么补测"。宁可文档里挂着一条待办，也不能写"已验证"却没验过 —— 这份文档会被别人当事实引用。
3. **警惕循环验证**。拿自己写的 SQL 去对自己实现的接口，两边同源同错也发现不了。基准要独立：走框架自己的读取路径、或页面上的真实展示。在"回归证据"折叠块里写明基准是什么。
4. **只写接口契约，不教调用方怎么实现**。字段含义、判定口径、边界、失败行为要写全（这些调用方必须知道）；组件怎么改、样式怎么写、改哪几个文件 —— 不写。
5. **示例里的环境地址要标注**，注明是本地/测试环境，联调需换域名。

## 画法：按「参考手册」画，不是按「阅读页」画

前端读接口文档是**扫读、跳读、对齐着看**，不是从头读到尾。手册的画法是标题有线、表格有格、代码是框、粗体标句眼，**全页重量均匀，靠内容分层**；阅读页的画法靠留白和灰度分层，在这个场景下天然吃亏，文档越小越吃亏（留白在大文档里是呼吸，在小文档里是空）。

**布局：`body` 本身就是那根居中的列，不要只把列给 `<main>`。**
`body{max-width:980px; margin:0 auto; padding:32px 24px 80px}` —— 标题、目录、正文**全在列里**。只给 `<main>` 设列宽是个隐蔽的坑：列外的元素（目录盒、通栏页眉带）没有任何宽度约束，**笔记本宽度下目录盒会横跨整屏**，而这个区间恰好是宽屏测不到、用户天天在看的。通栏页眉带还会让底线横穿 fixed 侧栏。

侧栏目录 `position:fixed; left:max(16px, calc(50% - 716px))`，只在 `min-width:1450px` 出现；窄屏改用正文里的目录盒 + 右下角回顶按钮；打印时反过来。**目录只在 HTML 里维护一份，用 JS 克隆到侧栏**——两份手工维护必然走样。

> 测响应式**必须包含 1366 和 1440**，不能只测 1600/2400。很多布局 bug 只在「窄于侧栏断点、宽于手机」这一段出现。

**最容易犯的错是层级画反**：结构元素（标题、表格、端点清单、鉴权说明、最重要的那一行字段）全用最轻的笔，证据元素（代码块）用最重的笔。读者眼睛先落到代码上，再回头找结构，找不到——这就是「说不上来哪里不好但一比就分得出」的来源。具体做法：

- **代码块用浅底 + 1px 边框，不要深色实块。** 深色块是白纸上最重的元素，会抢走本该给标题和表格的注意力；它还是一座孤岛，语法配色、`::selection`、打印覆盖、滚动条色都得单独维护，漏一项就出 bug（深色块配全局 `::selection` 浅色 = 选中即消失，而选中复制正是这类文档的第一用途）。浅色块和表格共用同一根边框、同一个底色，天然是同一家的「框起来的数据」。想想自己的打印样式——如果那里写的是浅色，屏幕上就不该是深色。
- **表格给完整边框 + 表头底色。** 五列参数表要横向追行，网格是给眼睛用的轨道。斑马纹和 hover 顺手加。
- **h2 加底线**，章节边界别只靠留白。
- **粗体标操作句。** 每条注意事项都把「该怎么做 / 别怎么做」加粗，扫读时要能抓到句眼。
- **灰色只给真正次要的东西。** 表头、字段类型列、「替代哪个老接口」都是实信息，不能用最淡的灰。所有正文对白底至少 4.5:1。
- **鉴权、必填、可能为 null 这类信息不能降成灰色脚注**，它们是调用方最先要找的。
- **最重要的那一行要给整行底色**，不是 2px 细条。
- 每个代码块配复制按钮，**带 `execCommand` 回退**——这份文件常被双击从 `file://` 打开，那种来源下 `navigator.clipboard` 不可用。
- **只做一套浅色主题，不要 `prefers-color-scheme`。** 文件会被转发、会被打印，所有人应该看到同一份。
- **打印时目录不能消失**，把侧栏变成正文顶部的一段清单。
- h2 悬停出 `#` 锚点，十行代码，「你看第 3 节」能直接发链接。

## 内容上容易翻车的几点

- **如果接口分两端/两态，出现顺序全文必须一致。** 这种文档最难的点就是"两端不同"，顺序一会儿门户在前、一会儿工作台在前，读者每次都要重新确认哪边是哪边。挑一个当锚点（通常是端点表的顺序），全文照办。不分两端就没这回事，别硬凑。
- **语义色不要一色两用。** 别让"某一端的身份色"同时兼任警告色——否则一个讲 A 端问题的警告框会涂着 B 端的颜色。警告给独立色相。
- **同一个概念别拆成两节。** 出现过"失败与边界"挂在示例下、"边界与约束"另起一节的情况，查"传空值会怎样"的人有两个候选。合并。
- **每个布尔字段都要有 true 和 false 两种样例。** 只给一种，读者会怀疑另一种是不是永远不出现。
- **首部的总括话术要和正文的"待补验证"对得上。** 写了"结论均取自实跑"又挂着未验证项，就是自相矛盾。
- **失败行为表必须给状态码和真实响应体。** 只写「令牌验证失败」没用——前端第一个问的就是「401 还是 200 带错误体」「body 长什么样」。每一行都去实跑一次抄回来。
- **别只讲「是什么」，要讲「你会怎么踩坑、为什么这么设计」。** 好文档的密度体现在注意事项里：为什么没有分页、为什么传错 id 返回 400 而不是空列表、两个接口对同一种数据口径为什么不同且是有意的、以后扩展会不会影响调用方。这些写代码时都想过，别烂在脑子里。

## 必备内容

- 端点 + Method + 鉴权方式
- 请求字段表：字段 / 类型 / 必填 / 业务含义 / **实跑用过的真实示例值**
- 有请求体的接口（POST/PUT/PATCH）：请求体字段表 + 一份实跑发出去的请求体示例
- 响应字段表：同上；本次新增的字段用 `class="new"` 高亮
- 完整请求响应示例，成功 + 失败各一份
- 业务错误码 + 触发条件；没有错误码就写明实际行为（如"查不到返回空数组，不报错"）
- 边界与约束：分页参数、字段长度、枚举取值、已知退化行为、可配置项
- 改动历史：本次新增/变更了什么 + 日期

## 用模板

复制 `assets/template.html`，替换 `{{...}}` 占位，删掉用不上的块。模板 body 是一份可直接改的占位骨架，class 与样式表已对齐——**不要自己发明 class**，样式表里没有的不会生效，而且没有任何报错。

**默认单栏。** 宽度只花在真正需要并排的那一处：找出文档里唯一「内容本身要左右对照」的地方（比如同一对象在两种口径下的两份响应），用 `.split` 局部并排，其余全宽。别架一整栏常驻右侧代码栏——判据是**如果它需要靠滚动切换面板才不显得空，它就是正文的摘要，必然重复**；当前章节的摘要，对正在读当前章节的人来说，定义上就是重复。

几个表达装置，**有对应内容才用，没有就整块删掉，别当装饰**：

| 装置 | 什么时候用 |
|---|---|
| `.end.a` / `.end.b` 圆点 | 接口分「两端/两态」（门户 vs 工作台、发布 vs 草稿）时，两种颜色贯穿全篇标记。**全文出现顺序必须一致**，挑一个当锚点后照办。片段在模板末尾的可选块注释里 |
| `.split` 左右对照 | 同一对象在两端的两份响应这类最易踩坑的点。全文通常只用一次，片段同在那个可选块注释里 |
| `.warn` + `.tag.todo` | 未验证项、已知缺口。如实写，别省略也别含糊 |
| `.tag.ok` | 给某节标「已实跑」 |
| `tr.new` | 本次新增的响应字段，整行标绿 |
| `.verb` | 端点表里的方法徽标，底色按修饰类分：`.verb.get` / `.post` / `.put` / `.patch` / `.delete` |
| `<details>` | 回归证据、对拍输出这类「要留档但不该占正文」的内容 |

**一份文档多个端点时**：每个端点一个 h2，它自己的参数表、请求体、响应字段、示例都挂在这个 h2 下的 h3；「边界与约束」「失败行为」「改动历史」全文共用一份、放最后；目录里一个端点一条。别按「参数表」「响应表」横切成大节，那样查一个端点要跳四个地方。

目录标签控制在 6 个汉字以内，否则侧栏会换行。`#toc` 里的 `href` 必须和 `section` 的 `id` 一一对应，滚动高亮才生效。章节号由 CSS 计数器生成，别手写。

## 交付

写完用浏览器实际打开看一眼再交付，**并且要量，不要只看一眼截图**（缩略图看不出问题）。至少在 `2560 / 1440 / 900 / 390` 四个宽度下用 JS 量一遍：

```js
const r=s=>{const b=document.querySelector(s).getBoundingClientRect();return Math.round(b.left)+'+'+Math.round(b.width)};
({w:innerWidth, body:r('body'), side:getComputedStyle(document.querySelector('.toc-side')).display, overflow: document.body.scrollWidth>innerWidth})
```

确认：内容列不随视口无限拉伸（超宽屏下版心居中）、`overflow` 恒为 false、窄屏侧栏折叠、目录高亮跟着滚动走。

> **视觉基调：照 API 文档站的行业惯例，别自由发挥。** 走过两次弯路才定下来：第一版通篇纯白、只有发丝线，读者说"一片白没有着力点"；第二版加深色页头 + 彩色端点卡片 + 分层地色，又被说"像廉价的 Swagger 仿制品"。定下来的做法：只用一个强调色（侧栏当前项、方法徽标），语义色（如区分两端）只出现在真正需要对照的那一两处，不要撒满全篇。
>
> **滚动高亮别用 IntersectionObserver 的「第一个进入视口者」** —— 上一节还没滚出去时它仍算进入，高亮和右栏都会滞后一节。用「最后一个越过顶部基准线（约 120px）」判断。两个必须处理的边界：**页面滚到底时最后几节永远过不了基准线**，要直接判给最后一节；**某些内嵌预览环境里 `scrollTo` 会滚动却不派发 scroll 事件**，所以 scroll 监听要配 IntersectionObserver 兜底触发（IO 只当触发器，判断仍走基准线）。

> **踩过的坑 · 超宽屏**：只给段落设 `max-width` 而表格不设，1440px 下看着正常，2000px 下正文很窄、表格铺满全宽，视觉撕裂。模板已经把列宽给了 `body`，表格天然在列里，别只给某个子元素设宽。

量完再把文件交付给用户——宿主有发送文件的能力就用它，没有就给出落盘路径，说明可直接转给对接方。
